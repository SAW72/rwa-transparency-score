# API history storage (package A4)

Local **Postgres-ready** schema + migrations for paid API history. SQLite remains the running path. **No hosted / paid Render Postgres** is provisioned here.

## What runs today

| Piece | Behavior |
|---|---|
| Default DB | SQLite at `RWA_API_DB_PATH` (default `data/rat_api.sqlite`) |
| Runner | `rwa_score.api.migrations.apply_sqlite_migrations` on `Store` startup |
| History rows | `score_history` — ticker, scored_at, score, band, payload_json, payload_hash, optional **`key_id`** (tenant) |
| Replay | `GET /v1/history/{ticker}` (paid) reads that key’s rows |

Render’s filesystem is still ephemeral. Stored attestation bytes and the API sqlite file disappear on spin-down, restart, or deploy. Two options, neither built in this change: a Render persistent disk on a paid plan, or Postgres (self-hosted; this repo does not provision paid Render Postgres). `render.yaml` may describe a second free web service for `/v1`; it does not add a disk or a paid database. The sqlite file on that service is still ephemeral.

## Revisions

1. **`001_initial`** — keys, usage, history, watchlists, webhooks, last_bands (tenant PK), deliveries.
2. **`002_history_tenant`** — nullable `score_history.key_id` + index `(key_id, ticker, scored_at)` so history can be isolated per API key without a hosted DB.
3. **`003_attested_payloads`** — exact canonical JSON bytes keyed by score hash (`attested_payloads`). Written when `GET /v1/attest/{ticker}` runs. Render free disk is ephemeral, so this file does not survive spin-down.
4. **`004_attestation_inputs`** — nullable `inputs_json` beside those bytes: the canonical scoring-input JSON, so `inputs_digest` can be recomputed without re-scoring.
5. **`005_attest_jobs`** — pending auto-attest queue, plus `tx_hash` and `attested_at` on the stored payload. Same ephemeral-disk limit until `DATABASE_URL` is set.

Applied versions live in `schema_migrations`.

## Postgres later (self-host only)

```bash
python -m rwa_score.api.migrations --dialect postgres
```

Prints `001` through `004` in Postgres dialect (`BIGINT GENERATED BY DEFAULT AS IDENTITY`, `DOUBLE PRECISION`, `ADD COLUMN IF NOT EXISTS`, `BYTEA` for the attested payload). Apply with your own `psql` when you choose to run Postgres **yourself**. Do not point the free Render web service at a paid Render Postgres from this package.

`RWA_API_DATABASE_URL` is accepted on `ApiSettings` as a **future** hook and is **not** opened by `Store`. SQLite `RWA_API_DB_PATH` stays authoritative.

## Attestations without stored bytes

`verify` only checks canonical JSON already in `attested_payloads`. An on-chain hash from before migration `003`, or from after a free-plan spin-down wiped the file, has no row. `verify` does not re-score, exits `2`, reports `stored: false`, and says **pre-fix attestation, stored payload unavailable**. `--fixtures`, `--api-url`, and `--api-key` warn and do not rebuild that payload. Re-run `GET /v1/attest/{ticker}` to store a new payload. `as_of` is attest time (the Unix second when that payload is hashed), so the new hash will not equal the old on-chain hash. `data_as_of` is the provider observation time when the report already has one. Keep the original bytes yourself if you still need the old preimage. A stored payload that predates `as_of` / `scorer_version` / `inputs_digest` / `data_as_of` is flagged `legacy` and is still checked against its own bytes. A `--db` path that does not exist is an error (exit `1`); verify does not create an empty database.

## Known limitation: ephemeral payload store

The payload store is the sqlite file on the service disk. On Render's free plan that disk is ephemeral, so a spin-down drops every stored payload and the attest queue. `verify` then has nothing to check. This package does not add a disk or a database. Spencer can attach a Render persistent disk (paid plan) or run Postgres and apply `python -m rwa_score.api.migrations --dialect postgres` himself.

## Compatibility

Existing SQLite files created before this runner still work: `001` uses `CREATE TABLE IF NOT EXISTS`, then `002` adds `key_id` when missing. The older unscoped `last_bands` table is still rewritten by `Store._migrate_last_bands`.
